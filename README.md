# Generador de planos de ARMADURAS (assemblies) — Revit 2027

Pipeline de graphs de Dynamo (4.0, CPython3, **sin paquetes externos**) para documentar
las **armaduras de acero (Structural Rebar)** de los assemblies de Revit: sheets, vistas
de planta y corte mostrando el refuerzo, distribución en láminas y acotado, según el
estándar de referencia LDS25-099058-PL-330-006/007. Es la variante orientada a armaduras
del generador de planos de fundaciones (T001): mismo contrato de nombres, sin pasos
extra en Dynamo Player. Son 6 graphs (00–05, ver la tabla de orden más abajo): **00
Asignar Partition** (va primero, clasifica las barras y escribe el parámetro `Partition`
que los demás necesitan), **01** vistas de assembly, **02** calcular y crear láminas,
**03** colocar vistas, **04** cotas y tags, **05** tabla de despiece. (Historia de la
numeración: el antiguo 05 de tags se integró al de cotas el 2026-07-15; el antiguo 07
de leyendas se eliminó el 2026-07-21; el antiguo 04 se eliminó el 2026-07-22; el
2026-07-24 se reordenó todo para que Asignar Partition quede primero — antes iba último
como paso opcional. Las referencias históricas a números de paso en las notas de abajo
son de la numeración vieja salvo que se indique.)

## Qué lo hace un pipeline de ARMADURAS (y cómo convive con el de Formas)

Este pipeline corre **sobre el mismo modelo** donde ya corrió la rutina de Formas (T001)
y está diseñado para **no tocar nada de esa rutina**:

- **Set de vistas paralelo, con sufijo ` - ARMADURA`** en el nombre interno: planta
  `FN-1001 - ARMADURA`, cortes `FN-1001 - ARMADURA - CORTE A/B`, callouts de pedestal
  `FN-1001 - ARMADURA - PEDESTAL {tipo}`. Las vistas de Formas (`FN-1001`,
  `FN-1001 - CORTE A/B`) nunca matchean por nombre, así que ni la idempotencia ni el
  retrofit del 00 las alcanzan (lección del 2026-07-14: la primera corrida usaba los
  mismos nombres de Formas y les pisó template y título a las 48 vistas existentes).
- **Marcadores de sección cruzados ocultos (00, automático)**: los cortes/callouts de
  Armaduras dibujan su línea de sección también en la planta de Formas del mismo
  assembly (y viceversa: ambos sets son vistas del mismo assembly). El 00 oculta por
  elemento (`View.HideElements` sobre el marcador, categoría *Viewers*) el que no
  corresponde en cada planta: la planta de Formas queda solo con sus cortes y la de
  Armaduras solo con los suyos. Idempotente (salta los ya ocultos).
- **Dos view templates independientes en el 00 (2026-07-14)**: input "View template para
  la planta" (default `ARMADURA PLANTA DYN`, reemplaza a `ARMADURA PLAN GRAL`) se aplica
  solo a la planta; input "View template para los cortes y callouts (secciones)" (sin
  default todavía) se aplica a los cortes A/B **y** a los callouts de pedestal, porque
  ambos son secciones. Antes un único template gobernaba las tres, lo que obligaba a que
  el mismo template sirviera para planta y cortes a la vez — problemático porque las
  secciones necesitan ocultar la categoría *Sections* (ver más abajo) y la planta no.
  Si el nombre de cualquiera de los dos no matchea ningún template del proyecto, el log
  avisa y lista los templates disponibles (antes esto no estaba implementado pese a que
  el README ya lo prometía). Sigue valiendo la regla de siempre: ningún template
  **debe** controlar la escala (rompe la escala automática) ni la visibilidad de la
  categoría *Sections* en los cortes. (Confirmado en la corrida del 2026-07-14 que se
  aplica sin problema a las Detail Views de assembly; si en otro proyecto el template
  fuera de un tipo incompatible, el 00 lo avisa en el log en vez de fallar.)
- **Barras "Unobscured" por vista (00, automático, sin input nuevo)**: mostrar las barras
  por delante del hormigón es un estado **por elemento y por vista** (*View Visibility
  States* de Revit) que un view template **no puede** controlar — el template solo aporta
  el color. El 00 recolecta las barras del assembly (miembros directos + las hospedadas
  en cualquier miembro, vía `RebarHostData`) y les activa `SetUnobscuredInView` en cada
  vista que crea. Idempotente: al re-correr también retrofitea vistas ya existentes, y
  solo toca las barras que faltan. Si un assembly no tiene ninguna barra, el log avisa
  (`el assembly no tiene barras de refuerzo`) — la lámina de ese assembly saldría vacía
  de armadura y hay que revisar el modelado, no el script.
- **Presentación "primera y última barra" en la planta (00, automático, 2026-07-15)**:
  para sets de varias barras (ej. Layout "Number with Spacing"), la planta aplica el
  modo de presentación `RebarPresentationMode.FirstLast` (`Rebar.SetPresentationMode`) —
  es el mismo checkbox "Show First and Last Rebar in Rebar Set" que aparece al
  seleccionar la barra a mano en Revit. Evita que el set completo se dibuje amontonado
  en la planta. Se aplica **solo en la planta**, no en cortes ni en los callouts de
  pedestal. Se salta automáticamente (`CanApplyPresentationMode` devuelve False) para
  barras que no forman un set (ej. Layout "Single"), sin necesidad de releer el Layout
  Rule — no depende de la lógica de tags de 03. Idempotente: solo cambia las barras que
  no están ya en ese modo.
- **Barras de pedestal en la planta: solo `Partition` = `PPL-PPL` (00, automático,
  2026-07-15, ampliado 2026-07-20, regla de negocio definida con jefatura)**: no es
  un conteo por assembly (ese era el criterio hasta el 2026-07-20) — es un filtro
  **por barra individual**. Toda barra hospedada en una instancia "tipo pedestal"
  (cualquier familia cuyo nombre contenga "Pedestal", case-insensitive: además de la
  familia pura `C-Pedestal` existen familias **combinadas** fundación+pedestal en
  una sola pieza, ej. `C-Fundacion+Pedestal`, `C-Fundacion+2-Pedestal`, donde el
  sub-componente que hospeda la barra — ej. una capa `C-CapaCimiento` como "G35" —
  cuelga *directo* de esa familia combinada vía `SuperComponent`, sin nivel
  intermedio "solo pedestal" separable) se muestra en la planta **únicamente** si su
  parámetro de instancia `Partition` (texto plano, `AsString()`, mismo patrón que
  `leer_partition` del 03) empieza con `PPL-PPL` — la armadura principal/
  longitudinal del pedestal. Cualquier otro tipo de armadura del pedestal (estribos,
  etc.) se oculta, sin importar cuántos pedestales tenga el assembly (antes del
  2026-07-20, con 2+ pedestales se ocultaba TODA la armadura de pedestal por
  ambigüedad de a cuál pertenecía cada barra, y con 0 o 1 se mostraba todo sin
  filtrar; el filtro por `Partition` reemplaza esa ambigüedad porque ya no importa a
  qué pedestal pertenece la barra, solo su tipo). Las barras que **no** son de
  pedestal (zapata/radier: `PPL-SUP`, `PPL-INF`, `SEC-LAT`, `SEC-RFZ`) nunca pasan
  por este filtro, siguen mostrándose igual que siempre. Identificación del host:
  `Rebar.GetHostId()` para llegar al host y de ahí `FamilyInstance.SuperComponent`
  hacia arriba hasta dar con una de las instancias de pedestal del assembly
  (comparación por `ElementId`, no por nombre — el nombre de familia solo se usa
  para identificar qué instancias son "tipo pedestal"). El 00 las oculta
  explícitamente en la planta (`View.HideElements`, no solo deja de aplicarles
  Unobscured/First-and-Last). **Cortes A/B y los callouts de pedestal siguen
  mostrando toda la armadura del pedestal a propósito** — el filtro es solo para la
  planta. El 03 no se tocó con este cambio: nunca tageaba armadura de pedestal (su
  filtro `PARTITIONS_TAGEABLES` no incluye `PPL-PPL`), así que el comportamiento de
  tags no varía.
- **Títulos en lámina**: planta `FN-1001 - ARMADURA` (Title on Sheet, 00) y cortes
  `FN-1001 - ARMADURA - CORTE {letra}` (02).
- **Tabla de cantidades (06) con filtro propio**: marca los miembros con el parámetro
  compartido **`SHEET_ARMADURAS`** (si no existe en el proyecto, el 06 lo crea y bindea
  a las categorías de modelo automáticamente) — **no** usa `Comments`, que es el filtro
  de las tablas de la rutina de Formas: pisarlo las vaciaría, porque los miembros son
  los mismos elementos físicos en ambas rutinas. Los schedules se llaman
  `TBL_ARMADURAS_{sheet}` (nunca colisionan con los `TBL_ASSEMBLIES_*` de Formas), y el
  06 solo considera sheets que tengan plantas de ARMADURAS colocadas.
- **Tags de familias (ex-05, ahora en el 03)**: el antiguo paso 05 se eliminó del
  pipeline (2026-07-15) — su tagueo de familias vive en el 03, automático y sin
  selección, solo en plantas de ARMADURAS cuyo assembly tiene 2+ tipos distintos de
  `C-Pedestal` (ver fila 3 de la tabla).
- **Nombre de lámina por defecto** en el 01: `ARMADURAS - HOJA 01`. Las láminas de
  Formas nunca reciben vistas nuevas (el 02 omite sheets que ya tienen viewports).
- El input "Tipo de vista para cortes (símbolo)" conserva el default `02_FORMAS` (define
  solo el símbolo de corte). Si la oficina usa un tipo de vista propio para cortes de
  armadura, escribir su nombre exacto ahí — si no existe, el log lista los disponibles.

## Requisitos

- Revit 2027 (los .dyn están guardados en formato Dynamo 4.0).
- Assemblies ya creados en el proyecto (ej. `FN-1001`, `PD-1002`).
- Viñetas (title blocks) cargadas en el proyecto.
- Ningún paquete de Dynamo: todo es out-of-the-box + Python embebido.

**Primera vez en una máquina nueva**: abrir cada .dyn en Dynamo (no en Player), correr y
guardar. Eso registra los inputs para Dynamo Player. Después, todo se opera desde Player.

## Orden de ejecución

| # | Graph | Qué hace |
|---|-------|----------|
| 0 | `00_Asignar Partition.dyn` | **Va primero (opcional en modelos que ya traen `Partition`).** Recorre las barras del modelo y clasifica cada una por tipología con un árbol de decisión (`SEC-EST` estribo, `RFZ-RFZ` refuerzo, `SEC-LAT` cerco lateral, `PPL-PPL` longitudinal de pedestal, `PPL-INF`/`PPL-SUP` canastillo inferior/superior), y le **escribe el parámetro `Partition`** que el 01 (vistas) y el 04 (cotas) necesitan para sus filtros. Solo rellena barras con `Partition` vacío (no pisa lo cargado). Pinta cada barra con su color en la vista 3D indicada — `PPL-INF` **amarillo** `255/255/0` (2026-07-24; antes azul, brevemente oliva), `PPL-SUP` rojo, `SEC-LAT` verde, `PPL-PPL` naranjo, `SEC-EST` celeste, `RFZ-RFZ`/`SEC-RFZ` magenta — y deja las que no logra clasificar sin color, aisladas en la vista `ARM - BARRAS SIN PARTITION` para asignarlas a mano. Tiene modo **Solo AUDITAR** (default) que no escribe nada, solo compara contra los `Partition` ya cargados. **Regla `RFZ-RFZ` (2026-07-24, pedido de Javier)**: barra con Shape (`RebarShape`) `TIPO-3` o `TIPO-1 RFZ` **y** tipo `ø 10 mm / Traccion` **o** `ø 10 mm / Amarre` (mismas barras, distinto sufijo de tipo — 2026-07-24) → `RFZ-RFZ` (magenta); se evalúa temprano en el árbol (dato explícito del modelador) y no choca con `SEC-LAT`, que comparte la forma `TIPO-3` pero es ø16. **Regla de muros (2026-07-24, pedido de Javier)**: si el host de la barra es un **muro** (categoría `Walls`/`OST_Walls`; helper `es_host_muro`), su `Partition` se decide **solo por orientación** (helper `es_vertical`): **vertical → `PPL-PPL`**, **horizontal → `SEC-LAT`**. Esta rama corre **antes que RFZ-RFZ** a propósito: las barras de muro tienen Shape `TIPO-3`/`TIPO-1 RFZ` + tipo ø10, así que si no se atajaran acá caerían todas en `RFZ-RFZ` (magenta) — la regla RFZ-RFZ es solo para el refuerzo de fundación/zapata, no para muros. Solo aplica a barras hospedadas en muros; las de fundación/zapata siguen por el resto del árbol sin cambios. (Los estribos `StirrupTie` de muro, si los hubiera, siguen saliendo `SEC-EST`, que se evalúa antes.) **Regla de vigas: TODO `PPL-PPL` salvo estribos (2026-07-29, pedido de Javier)**: si el host de la barra es una **viga** (categoría `Structural Framing`/`OST_StructuralFraming`; helper `es_host_viga`), su `Partition` es **`PPL-PPL`**, sin análisis geométrico. La **única excepción** son los estribos, que ya salieron `SEC-EST` en la primera regla del árbol. Reemplaza el paso previo por `clasificar_viga()`: en las vigas de este modelo el reparto `SEC-LAT`/`PPL-SUP`/`PPL-INF` no aportaba y metía ruido — todo el armado longitudinal de viga se trata como principal. La rama sigue corriendo **antes que RFZ-RFZ** por la misma razón que los muros (las barras de viga pueden compartir Shape/tipo con el refuerzo de zapata y caerían en magenta). `clasificar_viga()` **sigue en uso para las zapatas** (regla siguiente). **Regla de zapatas — por proximidad a caras (2026-07-24, pedido de Javier; hasta el 2026-07-29 la compartían las vigas)**: `clasificar_viga()` (ahora solo para `es_host_zapata` — Floors / Structural Foundation) ya **no** mide por altura relativa en el bbox (tercios); mide la **distancia perpendicular** del centro del tramo principal de la barra al plano de cada **cara plana real** del host (`caras_planas_host()`, recorre sólidos con `Volume > 0`, recursivo en geometría anidada vía `GeometryInstance.GetInstanceGeometry()`). Cada cara se clasifica por su normal: `|normal.Z| > 0.9` → cara **horizontal** (superior/inferior), `|normal.Z| < 0.1` → cara **vertical** (costado/lateral). La barra se asigna a la cara más cercana: más cerca de una **lateral** → `SEC-LAT`; más cerca de una **horizontal** → `PPL-SUP` si el centro de la barra está sobre el medio del host, `PPL-INF` si está bajo — empate dentro de `TOL_LAT_MM` (5 mm) o si falta un lado → `SEC-LAT` (fallback conservador, para no perder una lateral real). **Por qué se cambió**: la 1ª versión (tercios de altura del bbox, constante `FRAC_CARA_VIGA`) fallaba con barras `SEC-LAT` modeladas "Parallel to Work Plane" desde la cara superior/inferior — su centroide caía en el tercio sup/inf del bbox por altura aunque geométricamente estuvieran pegadas a un costado; "funcionaba igual que siempre" pese al cambio. Corre **después del check de verticalidad** (así los pedestales verticales de familias combinadas salen `PPL-PPL` primero) y reemplaza a la lógica de malla (que queda de fallback para otros hosts). Estribos siguen `SEC-EST` (se evalúan antes, sin cambios). **Marcador "(LATERAL)" desactivado (2026-07-24)**: el criterio viejo de `SEC-LAT` por `Schedule Mark` = "(LATERAL)" se **comentó** — corría antes de la geometría y atrapaba las laterales por el texto manual, enmascarando el criterio geométrico ("funcionaba igual que siempre", detectado por Javier). Ahora `SEC-LAT` sale **solo por geometría**. Está comentado dentro de `clasificar()`, reversible. **`Schedule Mark` semántico (2026-07-29; ampliado a barras sueltas el 2026-07-30, pedido de Javier)**: además del `Partition`, el paso 0 normaliza el `Schedule Mark` de las barras. `Schedule Mark` es un parámetro de instancia de **texto libre** de Rebar que **Revit autonumera** al crear la barra (de ahí los `18` que se veían impresos) y que **no es único** — medido por MCP contra el modelo real, 8 barras distintas comparten el `18`. Su propósito original es identificar la barra en la tabla de despiece, pero en este proyecto los modeladores lo pisan a mano con una nota entre paréntesis, y **esa nota es la que sale impresa en la etiqueta Multi-Rebar Annotation del 04**. La nota se **deriva del `Partition`**, sin importar la cantidad de barras del set: host = **muro** → `(INT.-EXT.)`; `PPL-INF`/`PPL-SUP` → `(SUP.-INF.)`; `SEC-LAT` → `(LATERAL)`; el resto (`SEC-EST`, `PPL-PPL` de pedestal, `RFZ-RFZ`, `SEC-RFZ`) **no se toca** (los estribos usan el tipo de etiqueta `RecuentoSimple` del 04, no el de recuento doble). **Alcance ampliado a barras sueltas (2026-07-30, pedido de Javier)**: la 1ª versión solo tocaba **sets multibarra** (`Quantity > 1`), con el argumento de que en una barra suelta un recuento que vale para dos caras no significa nada. En la práctica es al revés: hay barras `PPL-SUP`/`PPL-INF` (y `SEC-LAT`) modeladas **sueltas**, y el 04 las etiqueta igual — de hecho es el Layout **`Single`** el que recibe el tipo de tag `RecuentoDoble_Corto` (`TIPO_TAG_POR_LAYOUT` del 04), o sea justo el de recuento doble —, así que salían impresas en la lámina con el número autonumerado de Revit. Ahora la regla depende **solo del host y del `Partition`**; `es_set_multibarra()` se conserva pero únicamente para desglosar el log (cuántas de las tocadas eran sueltas y cuántas de ellas estaban mal). Junto con eso, la rama de muro se acotó a `PARTITIONS_SM_MURO` = `PPL-PPL`/`SEC-LAT`: antes le ponía `(INT.-EXT.)` a **cualquier** barra hospedada en un muro, incluidos los estribos (`SEC-EST`, que según la regla no se tocan) — quedaba invisible mientras solo entraban sets multibarra, y con las sueltas adentro sí aparecía. La rama de **muro va antes** del mapa por `Partition`: las barras de muro salen `PPL-PPL` (verticales) o `SEC-LAT` (horizontales), así que por `Partition` las horizontales caerían mal en `(LATERAL)` — confirmado por MCP, los 25 `(INT.-EXT.)` del modelo son 10 `PPL-PPL` + 15 `SEC-LAT`, exactamente el reparto de la regla de muros. Se ejecuta como **2ª pasada** aparte del árbol de clasificación, para usar el `Partition` **efectivo** del modelo (incluidas las barras que el script no supo clasificar pero que ya traían `Partition`). **Pisa** lo que haya escrito, que es lo que normaliza las erratas. Respeta **Solo AUDITAR** (reporta cuántas corregiría, sin escribir). **Por qué se agregó**: la nota se escribía a mano y de forma despareja, así que muchas etiquetas salían con el número automático. Medido por MCP sobre el modelo real (619 barras): de las 33 barras `PPL-INF` multibarra —las únicas, junto con `SEC-LAT`, que reciben Multi-Rebar Annotation en la planta (`PARTITIONS_TAGEABLES` del 04)— **solo 6** tenían la nota; el `(SUP.-INF.)` estaba escrito sobre las `PPL-SUP` (45 de 68), que son la malla que **no** se etiqueta. Inventario previo de notas en el modelo: `(SUP.-INF.)` 56, `(INT.-EXT.)` 25, `(LATERAL)` 25, `(REFUERZO)` 8, `(SUP.)` 4, más dos erratas —`(UP.-INF.)` y `(EXT.-INT.)`— que la regla corrige. |
| 1 | `01_Vistas de assembly.dyn` | Por assembly: planta (`HorizontalDetail`) y **dos cortes perpendiculares que se cruzan al centro** (`DetailSectionA` + `DetailSectionB`, uno por cada eje del assembly), renombrados, con escala automática (ancho o largo > 2 m → 1:50, si no 1:25). **Detail Level**: planta y cortes quedan en `Coarse` (ver nota 2026-07-14 más abajo sobre por qué, pese a ser el nivel más bajo, ahí se ve el refuerzo); los callouts de pedestal siguen en `Fine`. El plano de corte de la planta se sube por encima del assembly (input en cm, default 30) para que nada aparezca cortado. En los cortes se ocultan los símbolos de corte (solo la planta los muestra) y se les aplica el tipo de vista del input "Tipo de vista para cortes" (default `02_FORMAS`, que define el símbolo de corte; si no existe en el proyecto, avisa con la lista de tipos disponibles y sigue con el default; vacío = no cambiar). En cada planta escribe el parámetro de vista `Cantidad_Inserto` = número de instancias de ese assembly en el proyecto (lo muestra el título `C_ConTitulo`; si el parámetro no existe en el proyecto, avisa una vez y sigue). El **título mostrado en lámina de la planta** es "{assembly} - ARMADURA" (vía *Title on Sheet* / `VIEW_DESCRIPTION`) — el **nombre interno de la vista** (`View.Name`) es también `{assembly} - ARMADURA` y los cortes `{assembly} - ARMADURA - CORTE A/B`: 01, 02, 03, 04 y 06 buscan las vistas por esos nombres exactos, no renombrarlas a mano. Aplica **dos view templates independientes** (2026-07-14): uno a la planta (input con el nombre; default `ARMADURA PLANTA DYN`, reemplaza a `ARMADURA PLAN GRAL`; vacío = ninguno) y otro a los cortes A/B y a los callouts de pedestal (input separado, sin default todavía, ya que ambos son secciones y necesitan poder ocultar la categoría *Sections* sin afectar la planta), y además marca las barras del assembly como **Unobscured** en cada vista y aplica a los sets de varias barras el modo de presentación "primera y última barra" **solo en la planta** (ver sección "Qué lo hace un pipeline de ARMADURAS"; `armaduras_del_assembly()` recorre `instancias_recursivas(ai)` para encontrar `RebarHostData` a cualquier profundidad de anidamiento, no solo en miembros de primer nivel — mismo fix 2026-07-20 que `rebar_del_assembly()` de 03, ver fila 3). **Far Clip Offset de los cortes (2026-07-20, R2 el mismo día)**: los cortes A/B por defecto veían con mucha profundidad de más (Revit calcula un offset automático al crear la sección, que puede ser mucho mayor que lo que realmente ocupa el assembly). `ajustar_far_clip_corte()` fuerza un **valor fijo** (`FAR_CLIP_MARGIN_MM`, default 500mm) en **todos** los cortes, sin importar la profundidad real del assembly — es el estándar de oficina pedido explícitamente por Javier. **Ojo**: una primera versión de este mismo día calculaba en cambio profundidad real del assembly a lo largo de `ViewDirection` + este margen (para no cortar geometría propia en assemblies profundos, lo que rompía silenciosamente las cotas/spot elevations/tags de 03 que referencian caras fuera del far clip — Revit las crea pero las borra en el regen siguiente sin avisar); se revirtió a pedido explícito, con esa consecuencia conocida y aceptada: en assemblies más profundos que `FAR_CLIP_MARGIN_MM`, el corte deja de dibujar la geometría más allá de ese plano y las cotas/tags del 03 que referencian caras ahí pueden desaparecer en el regen siguiente sin aviso — si eso pasa, es esperable, no un bug del script. Se reaplica en cada corrida, corrigiendo también cortes ya existentes. No existe un dropdown nativo de Dynamo para view templates sin paquetes, así que **si el campo queda vacío, el log siempre lista los templates cargados en el proyecto** (correr una vez para ver la lista, copiar el nombre exacto y correr de nuevo); si el nombre no coincide con ninguno, también avisa con la lista. El template no debe controlar la escala (rompería la escala automática) ni conviene que fuerce la visibilidad de la categoría Sections en los cortes (los dejaría de mostrar limpios). **"Crop View" (geometría) se activa siempre** (nuevas vistas y ya existentes; distinto del *Annotation Crop*, que se desactiva a propósito más abajo) — sin esto la vista muestra su extensión completa sin recortar, mucho más grande que el `CropBox` calculado, desperdiciando espacio en la grilla de 01/02 aunque el crop esté bien ajustado. El rectángulo del crop **no se dibuja** (`Crop Region Visible` = False) para que no aparezca como línea en la lámina, pero el recorte de geometría sigue activo. El **crop de la planta (ancho y alto) y el crop de los cortes (ancho y alto) se ajustan justo al borde del assembly** (input "Margen del crop, planta y cortes", default 5 mm de papel); esto también acorta la línea de sección que se dibuja en la planta, que antes salía mucho más larga que el assembly. El *Annotation Crop* se desactiva en las tres vistas para que cotas, cadenas y tags —que se colocan por fuera del borde— nunca queden cortados por este recorte (por eso es seguro ceñir también el alto del crop de los cortes: la cota de altura y la spot elevation superior de 03 quedan igual de visibles). Limitación conocida: si las anotaciones verticales quedan escalonadas, la cadena va al offset base (banda 0) y puede no alinear con las escalonadas. **Escalonado para que no se monten (2026-07-21, mismo día, pedido de Javier: "los tags se montan unos sobre otros… que sigan a la izquierda pero sin montarse sobre la zapata tampoco")**: el problema era que `posicion_afuera_assembly` manda TODAS las anotaciones de empuje-izquierdo al mismo borde del CropBox con el mismo offset → caen sobre la **misma X**, apiladas; y con el `offset_mm` por defecto (−10 mm, negativo, heredado de la planta) quedaban por **dentro** del borde, encima de la zapata. Fix **solo para el empuje izquierdo del corte** (el empuje hacia arriba se dejó igual, sigue usando `offset_mm`): (a) se arranca por **fuera** del borde con un clearance positivo dedicado en vez del `offset_mm` negativo — así dejan de montarse sobre la zapata; (b) **escalonado por bandas**: se lleva registro de la franja vertical de cada anotación ya colocada en ese corte; cada anotación nueva cuya franja choca con una ya puesta en la misma banda X se corre un paso más a la izquierda, repitiendo hasta encontrar una banda libre. **La franja se calcula sobre la ALTURA DEL TEXTO (el centro de la barra, donde queda el tag) ± `MARGEN_MULTIREBAR_CORTE_MM` (default 10 mm), NO sobre la extensión completa de la barra** (fix 2026-07-21, mismo día, tras ver el resultado con Javier: los sets verticales largos —estribos de pedestal, con bbox desde z=0 hasta toda la altura— tapaban toda la columna izquierda y empujaban lejísimos a los tags de la zapata, que están abajo, aunque sus textos no se pisaban por estar a alturas muy distintas; con la extensión de barra el algoritmo los creía superpuestos. Javier lo notó preciso: pasaba solo en assemblies con 2+ familias a distinta altura —pedestal + zapata—; con una sola familia adentro estaban bien. Basar el choque en la altura del texto lo resuelve: estribo (texto a media altura) y zapata (texto abajo) ya no chocan, la zapata vuelve a la banda 0 pegada al borde). Las que no chocan quedan en la banda 0 (pegadas al borde exterior), así solo se escalona lo justo. **Clearance y paso son SLIDERS del Player (2026-07-21, mismo día, pedido de Javier: la primera versión los alejaba demasiado y quería regularlos él mismo)**: `IN[4]` "Sep. tags corte al borde (mm)" (default 3, la separación de la primera anotación al borde del assembly — bajarlo las pega más) e `IN[5]` "Sep. entre tags corte (mm)" (default 8, el paso a la izquierda entre anotaciones que chocan — bajarlo las junta). Ambos en mm de papel (se escalan por corte). El colchón de detección de choques (`MARGEN_MULTIREBAR_CORTE_MM`) quedó como constante al tope del script — subirlo si dos tags a alturas distintas igual se pisan por el largo del texto. **Ojo (idempotencia)**: 03 salta las barras que ya tienen su Multi-Rebar Annotation en el corte, así que para ver un cambio de sliders hay que **borrar a mano las anotaciones existentes** del corte y volver a correr; y como se agregaron inputs nuevos, la primera vez hay que abrir el .dyn en Dynamo, correr y guardar para que el Player registre IN[4]/IN[5]. **Tipo distinto para estribos/amarras (2026-07-21, mismo día, pedido de Javier)**: si la barra es un `Rebar` individual cuya `RebarShape.RebarStyle` es `StirrupTie`, la Multi-Rebar Annotation del corte usa el tipo `RecuentoSimple+Info_S/Linea_Largo` (`NOMBRE_TIPO_MULTIREBAR_ESTRIBO`) en vez del tipo general `RecuentoDoble+Info_S/Linea_Largo` — solo aplica en los cortes, la planta no se tocó. Detección (`es_estribo_stirrup_tie`): `RebarShapeDrivenAccessor` no expone el `RebarStyle` directo (mismo problema que el Layout Rule, que tampoco tiene getter ahí) — se resuelve leyendo el parámetro de instancia "Rebar Shape" (`BuiltInParameter.REBAR_SHAPE`, una referencia a un elemento `RebarShape`), con fallback a buscar por nombre de parámetro si ese `BuiltInParameter` no aplicara en algún Revit; `RebarShape.RebarStyle` sí es una propiedad real de la API (no un parámetro), se lee directo una vez resuelto el elemento. Si el tipo `RecuentoSimple+Info_S/Linea_Largo` no existe en el proyecto, el bootstrap avisa en el log y esas barras caen de vuelta al tipo general — no se dejan sin anotar. **Escalonado hacia arriba (2026-07-21, pedido de Javier: "los sets se amontonaban", visto en un corte con varios sets horizontales de zapata a la vez)**: el escalonado por bandas de más arriba solo cubría el empuje izquierda/derecha — el empuje hacia **arriba** (sets horizontales, ej. varias barras de zapata a distintas posiciones a lo largo) no tenía ninguna lógica anti-choque, así que con 2+ sets horizontales en el mismo corte sus textos quedaban superpuestos e ilegibles. Mismo mecanismo de bandas pero con los ejes cruzados: la colisión se mide por posición **horizontal** (`RightDirection`) en vez de vertical, y el paso se aplica hacia **arriba** en vez de hacia el costado — cada set que choca horizontalmente con uno ya colocado en la misma banda sube un `paso_tags_corte_mm` más. Usa un margen propio más generoso (`MARGEN_HORIZONTAL_MULTIREBAR_CORTE_MM`, default 60 mm — mayor que el vertical porque tiene que cubrir el ancho del texto, no solo su alto). Mantiene la posición base original (`offset_mm`, no el slider de clearance que es solo para izquierda/derecha). **Multi-Rebar Annotation cerca de su propio pedestal (2026-07-21, mismo día, pedido de Javier: "identifiqué que en ese corte hay dos pedestales, pero todas las cotas de ambos pedestales se van hacia la izquierda y se juntan, ¿podríamos dejar más cerca de los pedestales a las que le corresponden para que se vea más equilibrada la vista?")**: hasta ahora, el empuje izquierda era un criterio fijo sin excepción — con 2+ pedestales en el mismo assembly, las Multi-Rebar Annotation de **ambos** terminaban amontonadas en el mismo borde izquierdo, sin importar dónde estuviera cada pedestal en el corte. Nueva función `resolver_pedestal_de_barra()` (mismo recorrido `SuperComponent` que `es_barra_de_pedestal`, pero devuelve el `ElementId` del pedestal específico en vez de solo `True`/`False`) identifica a cuál pedestal pertenece cada barra; `lado_derecho_pedestal_en_corte()` proyecta el centro de cada instancia "tipo pedestal" del assembly sobre `vsec.RightDirection` (el eje horizontal de **este** corte específico, cada corte tiene el suyo) y compara contra el promedio de todas — si el pedestal de la barra queda por encima del promedio (más a la derecha que el conjunto), la anotación se empuja hacia la **derecha** en vez de la izquierda, con `empuje_derecha_corte()` (mismo criterio geométrico que `posicion_afuera_assembly`, función compartida con la planta que no se modificó — esta es una función nueva, exclusiva del corte, que fuerza el empuje hacia el lado opuesto) y su propia banda de escalonado (`bandas_der_corte`, independiente de `bandas_izq_corte`). Solo aplica cuando el assembly tiene 2+ pedestales (mismo `pedestal_ids_ai` ya calculado para otros filtros) y la barra resuelve a uno específico — barras sin pedestal asociado (zapata) o assemblies con 0/1 pedestal siguen con el criterio fijo de siempre a la izquierda, sin cambios. |

## Convenciones (contrato entre graphs)

- **Nombre de la planta = `{assembly} - ARMADURA`**. Nombres de los cortes =
  `{assembly} - ARMADURA - CORTE A` y `{assembly} - ARMADURA - CORTE B`
  (perpendiculares entre sí, cruzados al centro del assembly). No renombrar vistas a
  mano entre pasos: 01, 02 y 03 buscan las vistas por estos nombres. Los nombres
  SIN el sufijo (`FN-1001`, `FN-1001 - CORTE A/B`) pertenecen a la rutina de Formas y
  esta rutina no los toca jamás. El título en lámina de los cortes muestra
  `{assembly} - ARMADURA - CORTE {letra}` vía *Title on Sheet* sin que el nombre
  interno cambie.
- Si hay **varias instancias del mismo tipo de assembly**, se documenta la primera.
- Distancias de anotación y márgenes se ingresan en **mm de papel** y se convierten con la
  escala de cada vista (mismo aspecto en 1:20 y 1:50).
- **Los cortes se identifican con letras** (A, B, C… y tras la Z: AA, AB…), únicas por
  lámina y asignadas en orden visual. El 02 escribe la letra en el *Detail Number* del
  viewport del corte — es lo que muestra el símbolo de corte en la planta — y el título en
  lámina queda `{assembly} - ARMADURA - CORTE {letra}` vía *Title on Sheet*. Las plantas
  conservan números. El nombre interno de la vista sigue siendo
  `{assembly} - ARMADURA - CORTE A` (no renombrar: es lo que usan 00/03 para
  encontrarla). Re-correr el 02 re-letra y re-titula los cortes ya colocados (los que ya
  tienen letra la conservan).
- **El título bajo cada vista lo controla el tipo de viewport**, no la vista. El 02 aplica
  tipos de viewport distintos por clase de vista: plantas → input "Tipo de viewport para
  plantas" (default `C_ConTitulo`), cortes → "Tipo de viewport para cortes" (default
  `C_Titulo_Seccion`); si el tipo indicado no existe todavía en el proyecto, lo crea
  (duplica uno existente, activa *Show Title = Yes* y asigna la familia de View Title —
  si no hay ninguna familia de ese tipo cargada, avisa: la línea aparece pero no el texto).
  Re-correrlo retrofitea el tipo y el espaciado de los cortes ya colocados. El título
  mostrado es el nombre de la vista (salvo que la vista tenga *Title on Sheet* definido).

## Idempotencia (qué pasa al re-correr)

- `00`: si la vista ya existe, la salta. Con "Recrear vistas existentes" = True la borra y
  rehace (esto también elimina su viewport si estaba colocada).
- `01`: si no hay vistas pendientes de colocar, no crea ninguna lámina. Los números de sheet
  ya usados en el proyecto se saltan.
- `02`: vistas ya colocadas y sheets que ya tienen viewports se omiten.
- `03`: salta vistas que ya tienen cualquier cota. Los Rebar Tags de la planta son
  idempotentes por barra (una barra tageada no se retoca), y los tags de familias
  (ex-05) por planta (se saltan si ya hay algún Multi-Category Tag en ella).
- `06`: salta sheets que ya tienen la tabla colocada. El `Comments` de los assemblies se
  vuelve a escribir en cada corrida (barato, mantiene la asignación al día si algo se
  movió de sheet).

## Mensajes de log frecuentes

- `no existe la vista ... (corre 00_Vistas de assembly)` — falta el paso 0 para ese assembly.
- `sin caras perpendiculares para la cota de ...` (03) — los elementos están rotados
  respecto a los ejes del assembly o no exponen caras planas en esa dirección.
- `SIN ESPACIO para N vistas` (02) — correr 01 para agregar las láminas que falten y volver
  a correr 02 (lo ya colocado se respeta).
- `el tipo seleccionado NO es una viñeta` (01) — elegir en el dropdown uno de los tipos
  que el mismo log lista como válidos.
- `no se encontro el tag "C-MultiCat : Modelo" ... para las familias de la planta (ex-05)` (03)
  — cargar la familia `C-MultiCat` (o crear el tipo `Modelo`) al proyecto; mientras
  falte, el 03 sigue con todo lo demás y solo omite ese tagueo.
- `N familias no admiten este tag` (03) — categorías que el Multi-Category Tag no
  etiqueta (p. ej. subcomponentes sin categoría taggeable); es informativo, no un error.
- `N tipo(s) de C-Pedestal (se requieren 2+ distintos), planta sin tags de familias` (03)
  — no es un error: ese assembly no cumple la condición para tags de familias (0
  pedestales, 1, o varios del mismo tipo).
- `Tipo de viewport {nombre} creado (duplicado de ...)` (02) — bootstrap: el tipo de
  viewport con título no existía en el proyecto, se creó automáticamente. Revisar su
  grafismo (fuente, tamaño de texto) en las propiedades de tipo si no coincide con el
  estándar del proyecto.
- `no se encontro el estilo de linea / tipo de texto ...` (06) — el nombre del input no
  coincide con ningún estilo/tipo de texto cargado en el proyecto; el schedule se crea
  igual con el default de Revit. Corrige el nombre del input y vuelve a correr (re-corre
  también actualiza el grafismo de las tablas ya creadas).
- `no se encontraron los campos [...] en la categoria Assemblies` (06) — el nombre exacto
  de un campo del schedule (por defecto se busca "Assembly Name" y "Count") no existe en
  este Revit; el log lista los campos disponibles para la categoría *Assemblies* para
  elegir el nombre correcto.
